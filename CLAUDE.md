# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Tank Battle" — a Battle City / Tank 1990 remake in **Godot 4.5** (GDScript, Forward+), extended with a Slay-the-Spire branching campaign map, RPG progression, in-battle structure building, and local 2-player co-op. All art is generated by headless Blender renders committed as PNGs; all sound is synthesized at runtime.

## Commands

Godot 4.5 lives at `C:\Godot\tools\Godot_v4.5-stable_win64.exe`. **`godot` on PATH is a 4.7.1 Steam build** — use the explicit 4.5 path for anything that writes to the project. (`project.godot` currently carries `config/features=PackedStringArray("4.7")`, meaning it *has* been opened in 4.7 at some point; don't make that worse.)

```powershell
$godot = "C:\Godot\tools\Godot_v4.5-stable_win64.exe"

& $godot --path .                                      # run the game (starts at title_screen.tscn)
& $godot --path . scenes/main.tscn                     # run one scene directly (skips title/map)
& $godot --headless --path . --check-only --script scripts/main.gd   # parse/typecheck one script
& $godot --headless --path . --editor --quit           # reimport assets after adding PNGs
```

There is **no linter**. Verification is `--check-only` per script, running the game, and an ad-hoc integration suite: `tools/test_*.gd` are `SceneTree` scripts (not GUT/GDUnit) run headless and manually, e.g.:

```powershell
& $godot --headless --path . --script tools/test_compile_all.gd        # loads every script/scene under res://, instantiates each scene
& $godot --headless --path . --script tools/test_gameplay_runtime.gd   # boots main.tscn, checks player/builder/sound wiring
```

Each prints `[FAIL]`/`❌` lines and exits non-zero on failure. `tools/run_tests.ps1` aggregates them:

```powershell
pwsh tools/run_tests.ps1                      # all of them (49 as of now; the runner globs test_*.gd)
pwsh tools/run_tests.ps1 -Filter shop         # just the matching ones
pwsh tools/run_tests.ps1 -Probe               # …plus the balance sampling probe (~4 min)
```

It exists because of a specific failure mode: a broken assertion in `test_shop_and_attack_speed.gd` manifested as Godot **hanging for 90 s** rather than erroring, and chaining them all into one command blows the 10-minute limit and gets killed — so the hang was misread as a timeout and went unlocated. The runner gives each test its own `-TimeoutSec` and reports `PASS`/`FAIL`/`TIMEOUT` as three distinct outcomes. It also appends one row per test to `logs/balance/testrun.jsonl`, which is what `python tools/analyze_balance_log.py --tests` reads to flag "this test suddenly takes 20× longer than its median" — the first symptom of that same class of bug.

The rest are feature-scoped (`test_state_and_save.gd`, `test_act_enemy_theming.gd`, `test_perk_stacking.gd`, `test_shop_gated_buildings.gd`, `test_flamethrower.gd`, `test_train_teleport.gd`, `test_gamepad_support.gd`, `test_laser_origin.gd`, `test_teleport_destination.gd`, `test_explosion_vfx.gd`, `test_tree_visibility.gd`, `test_oil_barrel_blast.gd`, `test_texture_mipmaps.gd`, `test_armor_plating.gd`, `test_player_power.gd`, `test_map_director.gd`, `test_splitter_enemy.gd`, `test_engineer_tank.gd`, `test_spider_tank.gd`, `test_pipe_conduit.gd`, `test_enemy_shield_tower.gd`, `test_roller_wall_and_stage2_destruction.gd`, `test_floor_map.gd`, `test_room_flow.gd`, …) — check for an existing one covering your area before writing a new script. `ls tools/test_*.gd` is the authoritative list; this paragraph is a sample, not an inventory.

The two room-system tests are split along a deliberate line: `test_floor_map.gd` checks the **generated graph** (connectivity, door symmetry, boss depth, special-room uniqueness — 200 seeds, no scene boot), `test_room_flow.gd` checks **walking around on it** (door latch/open states, the base spawning and despawning, the player instance surviving a transition with its HP, shop rooms opening the dialog). A floor can generate perfectly and still be unplayable, so neither subsumes the other.

**Three tests fail on a clean checkout and are not related to the room system**: `test_differentiated_enemies.gd` and `test_enemy_crusher.gd` (both `Parse Error: Function "get_tree()" not found in base self`) and `test_texture_mipmaps.gd` (35 sprites report no mipmaps at runtime despite every `.import` saying `mipmaps/generate=true`). Verify against `git stash` before assuming a change of yours broke them.

Two of those are project-wide gates rather than feature tests, and are worth running after any change that touches spawning or art: `test_compile_all.gd` and `test_texture_mipmaps.gd`.

`test_train_teleport.gd` is worth copying as a pattern: it drives `TrainFollowHelper` against `tools/_train_stub.gd` (a bare `Node2D` exposing only `history_positions` / `history_rotations` / `follow_distance` / `leader_node`) instead of booting `main.tscn`. The helper is duck-typed throughout, so the whole follow-and-teleport behaviour is testable without textures, physics, or a map — and the test was verified to fail against the pre-fix logic, not just pass against the new one.

### Regenerating art

Sprites are Blender Cycles renders (Blender 5.2 LTS at `C:\steam\steamapps\common\Blender\blender.exe`). Paths are derived from each script's own location — no hardcoded absolute paths.

Most of the earlier "four stacked generations" of build scripts were consolidated into three — but **the consolidation deleted producers without checking that the survivors reproduce the committed art**, and several stale ones are still in `tools/` (see "Stale build scripts" below). The three consolidated ones, plus the armor-plate renderer added after them:

| script | renders |
|---|---|
| `build_all_sokpop_assets_unified.py` | tanks, tiles, eagle, buildings, power-ups, map nodes, explosions, spawn stars, bullets — and saves `assets/blender/tank_battle_assets.blend` |
| `build_sokpop_animations.py` | muzzle flash, clay debris, shield bubble, shockwave, dust puff, damaged base |
| `build_sokpop_clay_ui.py` | title banner, clay buttons, HP hearts |
| `build_armor_plating.py` | `enemy_plate_t1/t2/t3` — the armor-tier overlays (see "Enemy toughness is integer and visible") |

```powershell
$blender = "C:\steam\steamapps\common\Blender\blender.exe"
& $blender --background --python tools/build_all_sokpop_assets_unified.py
& $blender --background --python tools/build_sokpop_animations.py
& $blender --background --python tools/build_sokpop_clay_ui.py
& $blender --background --python tools/build_armor_plating.py   # enemy_plate_t1..t3 (3 renders)
python tools/analyze_render_and_colors.py    # QA: per-asset clipping / luminance / saturation
python tools/qa_tank_models_and_clipping.py  # QA: tank sprite bounding-box / clipping check
python tools/qa_style_consistency.py         # QA: the regression suite — run this after any re-render
python tools/qa_style_consistency.py --vs HEAD   # …plus a per-sprite diff against a git ref
```

`qa_style_consistency.py` needs no Blender (numpy + Pillow only) and exits non-zero on `[FAIL]`, matching the `tools/test_*.gd` convention. Each check encodes a defect that actually shipped: `blank` (the nine grey-square UI icons from a missing `clear_scene()`), `seam` (tile_trees leaking background at every grid vertex), `tileseam` (colour discontinuity at tile joins — see below), `frame` (props silently rendered 0.82× too small by the wrong `ortho_scale`), `clip`, `palette`. Both `blank` and `seam` are self-tested — restoring the pre-fix sprite makes them fail with the original diagnosis.

`tileseam` is the colour counterpart to `seam` (which only looks at alpha): the image is fully opaque, yet tiling it shows a grid line. It compares the gradient *at the join* against the distribution of gradients *inside* the tile, rather than naively differencing the first and last row — a raised brick under directional light legitimately looks different above vs below, and those two halves compose into one correct mortar line when tiled, so a naive difference reports 36 on art that is fine. `TILESEAM_EXEMPT` downgrades three known-unfixed tiles to WARN (`tile_ice`/`tile_conveyor` are orphaned assets; `tile_electric_wall_f3` is an unrendered glow animation) because a permanently-red gate stops being read; it prints a hint when an exempt tile stops seaming so the list doesn't rot.

`clip` and `palette` report **`[WARN]` only, by design** — they cannot infer intent. `clip` can't distinguish a clipped shape from deliberate one-sided composition (`diorama_*` fills its bottom edge and leaves the top empty). `palette` measures contrast against the actual terrain tiles rather than saturation, because saturation is the wrong proxy: `enemy_missile` sits at 16% saturation yet reads perfectly on sand (dark body, huge luminance gap), while `enemy_armor` at 44% is the one that blends in. Whole-sprite colour distance is still only a proxy — a tank's dark treads and outline carry much of its silhouette — so it flags hue collisions for a human to judge, and never fails the build.

**Never run the unified script just to change one asset.** `build_all_sokpop_assets_unified.py::main()` re-renders all 240 tank frames plus every tile/building/power-up, so it will silently overwrite any uncommitted or untracked sprite work elsewhere in the tree. For tanks, use the targeted path instead — it imports `PLAYER_PALETTES` / `ENEMY_PALETTES` from the unified script (single source of truth, no duplicated palette):

```powershell
& $blender --background --python tools/rerender_tanks.py -- enemy_basic          # one set, 6 frames
& $blender --background --python tools/rerender_tanks.py -- --list               # show renderable names
& $blender --background --python tools/rerender_vfx.py -- explosion              # one VFX sequence, 6 frames
& $blender --background --python tools/rerender_vfx.py -- --all                  # all four sequences
& $blender --background --python tools/rerender_tiles.py -- tile_brick           # one terrain tile
& $blender --background --python tools/rerender_tiles.py -- --all --legacy-light # baseline: old point-light rig
```

`rerender_tiles.py` covers the five terrain tiles whose owner scripts were verified to still reproduce the committed art (`tile_brick`, `tile_steel`, `tile_trees`, `tile_sand`, `tile_water`). It deliberately **excludes** the orphaned tiles (`tile_ice`, `tile_hard_clay`, `tile_conveyor`, `tile_jump_pad`, `tile_platform`). `--legacy-light` re-renders with the old point-light rig, which is how you tell "this differs because I changed it" from "this script never reproduced the committed art" — run it and diff against `HEAD` before trusting any tile change.

`rerender_vfx.py` is the same idea for animated effects (`explosion`, `suicide_blast`, `dust_puff`, `muzzle_flash`). Those sequences are spread across three different owner scripts — `explosion` belongs to the unified script, `suicide_blast` to `build_suicide_and_mirage_assets.py`, the other two to `build_sokpop_animations.py` — and it imports each builder from its owner rather than copying geometry, so it never becomes a fourth place that can render the same sprite.

**Explosion-type sequences must dissipate, and `test_explosion_vfx.gd` enforces it.** Every one of these was originally sized by a monotonically increasing formula (`scale_factor = base + frame * step`), so the smoke drifted *outward and larger* forever: the old `explosion_5` covered 33.7% of the frame against the peak frame's 19.0%, i.e. the animation ended as the biggest, solidest blob it ever drew, then got cut off by the frame edge. Late frames must instead *shrink* `r_puff` while `span` keeps creeping out — the mass breaks into separate small puffs and total ink falls. The test asserts coverage peaks mid-sequence and the last frame is under half the peak; it was verified to fail on the pre-fix art with exactly that diagnosis. The same rule is why late frames use a hollow ring: a few big overlapping spheres read as one shaded ball, not as smoke.

`sokpop_common.py::warn_if_stray_meshes()` runs inside `setup_render_settings()` and prints `[WARN]` if the scene still holds meshes. That exists because `build_ui_character_art_replacements.py` once omitted `clear_scene()`, leaving Blender's default cube parked in front of the camera — it rendered 9 UI icons as identical flat grey squares that shipped unnoticed, since the render itself "succeeded". A missing `clear_scene()` now announces itself.

Alongside those three, `tools/build_*.py` accumulates ~30 one-off scripts for individual feature batches (e.g. `build_desert_mechanics.py`, `build_rpg_branch_and_train_assets.py`, `build_hard_clay_tile_asset.py`) — each still imports `sokpop_common` and follows the same conventions, but renders a narrower asset set for one feature rather than the whole game. Check whether an asset you need to touch already has a narrower script before adding to the unified one.

#### Stale build scripts — several no longer reproduce the committed art

**There is no mechanism making one script the owner of an asset.** Overlapping scripts just overwrite each other, so whichever runs last wins. A full re-render (v0.06322) surfaced three concrete cases, and there is no reason to think it found all of them:

- **`build_diverse_sokpop_tanks.py` was deleted (v0.06323)** — it was a stale duplicate. It rendered `player_tier0-3` + `player2_tier0-3` + `enemy_basic/fast/power/armor`, every one of which is already produced by `build_all_sokpop_assets_unified.py` (8) or `build_expansion_sokpop_assets.py` (4). Because it was added *later* than the unified script, any batch ordered by script age handed it the win — and its inlined `enemy_basic` was still the pre-v0.06321 near-white grey `(0.75, 0.78, 0.84)`, so running it silently reverted that palette. If you resurrect it from history, don't.
- **Tanks had two generations of geometry** until v0.06322 — diverse's hand-built meshes (which is what shipped) vs unified's parametric `build_sokpop_tank`. They are now all unified-generation. Changing one tank's palette via `rerender_tanks.py` is safe *because* it goes through unified; doing it any other way reintroduces the split.
- **`refine_all_assets.py` / `refine_buildings_and_tanks.py` had the wrong frame width.** They render `star/bomb/shovel/clock/helmet/life/repair_station/turret_gun` and were passing `ORTHO_SCALE_DEFAULT`; the committed sprites were 1/0.82 larger. Fixed by `ORTHO_SCALE_PROP = 2.7` (see below). Despite the name, these are renderers, not post-processors — run them *after* the unified script, never before.
- **16 orphaned assets — no surviving script reproduces them.** `tile_ice`, `tile_platform`, `tile_hard_clay`, `tile_conveyor`, `tile_jump_pad`, `icon_armor`, `icon_regen`, `icon_atk`, `icon_speed`, `treasure_key`, `treasure_chest`, `shield_station`, `wind_blower`, `node_challenge`, `diorama_shop`, `diorama_event`. Silhouettes match the committed art exactly (`d_cov` 0.00) but shading does not (`d_rgb` up to 31). Neither the pipeline nor the owner scripts have changed since these were committed in `4e1aeaa` (v0.06318), and running an owner script alone reproduces the same mismatch — so the committed art came from a script that has since been deleted. `tile_ice` was checked against *both* of its candidate implementations (`build_all_sokpop_assets_unified.py::build_sokpop_ice` at `d_rgb` 24.08, `build_ice_and_platform_assets.py::build_ice_tile` at 31.37) and neither matches; the other 14 have a single owner, so failing to reproduce proves the same thing by construction.

  **Nothing is broken in-game** — the committed sprites are fine and are what ships. The hazard is that running any of these scripts silently restyles those assets. Do not "fix" this by re-rendering them: that trades known-good art for output nobody has approved. If it ever gets addressed, it needs an art decision first (adopt the scripts' look, or rebuild the scripts to match the shipped look), not a re-render.

Before changing anything in `sokpop_common.py` (it feeds every script), **commit the working tree first**, then re-render, then compare every PNG against `HEAD`. Use two independent signals so you can tell "render settings changed" from "art got reverted":

- **alpha coverage / bounding box** — shaders cannot move these, so any change here is geometry or frame width;
- **RMS after a large Gaussian blur** — form and lighting. The blur radius must exceed the bump wavelength (~12px at 256px), or grain leaks into the low-frequency band and reads as an art change. 8px is too small; 24px works.

#### `tools/sokpop_common.py` owns the look — change it there, not in the build scripts

The three build scripts contain **only modelling code**; the entire render pipeline lives in `sokpop_common.py` and is imported (each script does a `sys.path.insert` on its own dir). They used to carry three copies of these helpers, which is how the art style drifted and how one bug needed fixing three times. Do not re-inline them.

Things that module deliberately enforces, each of which was a real defect:

- **`srgb_to_linear()` on every colour.** Blender node sockets are scene-linear; the palettes throughout the build scripts are written as sRGB. Feeding sRGB straight into `Base Color` brightens and desaturates everything (a `0.22` blue channel lands at `0.04`). Pass colours as sRGB and let `create_clay_mat()` convert.
- **`Standard` view transform, not AgX/Filmic.** AgX is a photographic tonemapper that collapses saturated highlights toward white — it costs roughly half the chroma on this palette. Over-exposure is controlled by the light budget instead.
- **A calibrated, deliberately flat light budget.** Point lights fall off with the square of distance; the old 16 W fill at 6 units contributed ~0.03 W/m², i.e. nothing, leaving one sun to do everything. Now ambient-dominant: World ambient 0.85 + a weak sun (0.9 W/m²) + two properly-scaled point lights. The flatness is the point — Sokpop separates forms by silhouette and flat colour, not by tonal range, and a deep light ratio drags a saturated colour's shadow side through orange→red→black, which reads as dirty rather than hand-painted.
- **`create_sokpop_lighting()` is idempotent** (it purges existing cameras/lights first). `build_sokpop_clay_ui.py::main()` calls it three times to switch resolutions; without the purge the hearts rendered under nine lights.
- **Surface irregularity.** `create_clay_mat()` adds noise→bump and colour mottle; `apply_uniform_clay_bevel()` applies seeded vertex jitter. Perfect primitives with uniform bevels read as injection-moulded plastic, not clay. `reset_jitter_seed()` at the top of `main()` keeps batches reproducible.
- **The bump/mottle noise deliberately stays on Generated (bbox-normalised) coordinates.** This means grain scale tracks object size rather than world size — a known inconsistency, and *anchoring it to world space has already been tried and rejected*. Sourcing the noise `Vector` from `ShaderNodeNewGeometry.Position` at 6.0 cycles/unit does converge grain scale in the 256px renders (large-vs-small object grain ratio 1.88× → 0.88×), but the game draws at `TILE_SCALE = 0.1875`, i.e. 256px → 48px. Measured on flat interiors at display size, cross-asset dispersion got *worse* (p90/p10 28.8× → 40.9×) and full-bleed terrain tiles lost 21% of their surface texture. What unifies is the wavelength; what the player sees is the contrast surviving a 5.33× downsample, and that also depends on per-material bump strength and curvature, which are not unified — plus 6.0 cycles/unit lands at ~2.3px wavelength on screen, right against the 2px Nyquist limit. If you reopen this, define the acceptance metric at 48px before touching the shader, not on the 256px renders.
- **Frame-width constants are load-bearing and easy to lose.** `ORTHO_SCALE_DEFAULT` 3.3 / `ORTHO_SCALE_TANK` 3.6 / `TILE_FULL_BLEED` 3.34 / `ORTHO_SCALE_PROP` 2.7. Pixel size is inversely proportional to `ortho_scale`, so passing the wrong one silently rescales the sprite while everything still "renders fine" — that is exactly how the eight prop sprites ended up 0.82× too small. `ORTHO_SCALE_PROP` was recovered by measuring alpha bounding boxes against the committed art (`3.3 × 0.82 = 2.706`); after the fix all eight match the committed versions pixel-for-pixel.
- **`TILE_PLATE_BLEED` 3.64 is for full-bleed base plates; `TILE_FULL_BLEED` 3.34 is not big enough for them.** The camera sees 3.30, so 3.34 leaves only 0.02 of overhang — but plates are bevelled 0.08–0.12, so the rounded, shaded rim stays *inside* the picture and every tile is drawn with its own border. Tiled, that is a quilt. A plate needs `half ≥ 1.65 + bevel`, hence 3.64. This does not rescale the visible pattern (brick/rivet coordinates are independent); only the plate, which is meant to overflow, gets bigger. `TILE_FULL_BLEED` was left alone on purpose — it has 37 call sites in scripts that are not being re-rendered, and changing it would silently desync all of them from their committed art.
- **Tiling terrain must be lit by sun + ambient only — `create_sokpop_lighting(seamless=True)`.** Point lights fall off with distance, so `KeyFill` at `(-2.5,-4,5)` and `RimFill` at `(0,+5,4.5)` impose a gradient *across* the tile: the +Y edge gets rim light the −Y edge never sees. Any positional gradient becomes a grid line when the texture tiles against itself. A SUN is parallel, so it lights every `(x,y)` identically and only varies with surface normal — bevel and bump shaping survive intact. The flag also nudges sun/ambient up ~10% to make back the ~0.31 W/m² the two point lights contributed.
- **A tile with height must be rendered as part of an infinite field, or its own shadows will not tile.** Bricks stand 0.26 above the mortar and the sun sits at 35°, so each casts a 0.371-long shadow — longer than the 0.205 mortar gap. Inside the tile every gap is shadowed by the brick beside it, but at the frame edge the brick that should cast into it belongs to the *neighbouring* tile, which is not in the scene; so the same mortar line rendered dark at one edge and lit at the other (seam gradient 36, worse than the tile's own brick edges at 33). `build_sokpop_brick` and `build_sokpop_trees` now emit periodic copies at ±`ORTHO_SCALE_DEFAULT`, culled by *shadow reach* rather than visibility — the tree canopy is ~1.97 tall, i.e. a 2.81 shadow, so a dome entirely outside the frame still darkens it. **Dedupe the copies**: the odd brick row has bricks at both −H and +H, and −H shifted by +P lands exactly on +H, producing coincident cubes that z-fight into a regular pattern of dark bricks.
- **`setup_stylize_compositor()` — posterize / pixelate, off by default.** Committed assets are the un-stylized version; turning it on changes the whole art style. It only works on top of the flat light budget above: posterizing a deep gradient slices out wrong-hue mid-bands (a yellow tank comes back red and black). Note this is *not* "bake lighting to texture then render unlit" — baking serves realtime 3D, and this pipeline already outputs pre-rendered PNGs with the lighting baked in by definition, so that round-trip is a no-op here.
- **Blender 5.x compositor API is not 4.x.** `scene.node_tree` is gone; a `CompositorNodeTree` node group hangs off `scene.compositing_node_group`. Inside it, source from `CompositorNodeRLayers` and sink into `NodeGroupOutput` — `CompositorNodeComposite` was removed, and wiring `NodeGroupInput` as the source silently yields a fully transparent image. `CompositorNodeMath` is now `ShaderNodeMath`, but `CompositorNodePosterize` / `CompositorNodePixelate` exist natively.

`tools/update_input_map.py` is also gone; edit `project.godot` directly for input actions.

## Architecture

### Scene flow

`title_screen.tscn` → `main.tscn`, via `get_tree().change_scene_to_file()`. All three modes (Campaign, Arcade, Daily Challenge) go straight from the title into `main.tscn`. There are **no autoloads**.

**A whole campaign floor lives inside one `main.tscn` instance.** Moving between rooms is `_clear_all()` + `_build_map()` in place — not a scene change. The reason is the two state layers below: player HP, invulnerability frames, train carriages and the live `rpg_mgr` all hang off nodes and instances, so a scene change per door would mean running the hand-written `sync_to_game_state()` / `sync_from_game_state()` field lists dozens of times per floor instead of twice. Rebuilding in place sidesteps that chain entirely.

`scenes/spire_map.tscn` and `scenes/stage_preview_dialog.tscn` **are gone** (v0.06324, the Isaac conversion). The branching-route screen was replaced by the HUD minimap, and the pre-battle briefing dialog has no place when you simply walk into a room. `event_dialog` survived unchanged — it only ever read and wrote `GameState`, so it was reparented from the spire scene onto `main.tscn`'s HUD and now triggers on entering an event/rest room. The shop went further: it is no longer a dialog at all (see "The shop is a room, not a menu").

### The two state layers (most important thing to get right)

- **`GameState`** (`scripts/game_state.gd`) — a `RefCounted` with only `static var`s, used as a pseudo-singleton because statics survive scene changes. Holds mode/player count, act/floor position, campaign gold, level, tier, lives, perks, structure stock, the generated room graph (`floor_rooms`, replacing the old `spire_nodes` / `spire_connections`), and the `battle_type` + `challenge_mode` that tell `main.gd` which encounter to build.
- **`RPGManager`** (`scripts/rpg_manager.gd`) — a per-battle instance owned by `MainGame.rpg_mgr`, holding live XP/level/gold and stat multipliers, emitting `stats_changed` / `leveled_up` / `gold_changed` to the HUD.

These two are **manually synced**, not shared: `main.gd::start_game()` copies `GameState` → `rpg_mgr` on entry, and `_game_over()` / `add_gold()` / `_on_rpg_level_up()` copy back. Adding a new persistent stat means touching both sides plus the copy points **plus `save_campaign()`/`load_campaign()`**, or it silently resets between floors or between sessions.

**`tools/test_persistence_roundtrip.gd` enforces that instead of trusting you to remember it.** Both `save_campaign()`'s dictionary and `sync_to/from_game_state()` are hand-written field lists, and omitting a field from either produces no error — the value just quietly reverts. The test reflects over `get_property_list()` on both classes (never a hand-copied list, which is how the template test once drifted to covering 36 of 50), stamps every field, round-trips it, and diffs. A field added later is required to persist **by default**; exempting one means adding it to `EXEMPT`/`RPG_EXEMPT` with a stated reason. Verified by deleting `"run_seed"` from `save_campaign()` and `GameState.regen_lvl = regen_lvl` from `sync_to_game_state()` — both were caught by name.

Two methodology traps this test documents in-line, both of which produced false results while it was being written:

- **Deep-copy the expected values.** Dictionaries and arrays are references, so stashing `stamped[n] = v` and then calling `reset_campaign()` — which does `unlocked_perks.clear()` — empties the *baseline* too, and a successful round-trip reads as a failure.
- **Clobber with a sentinel between save and load; don't rely on `reset_campaign()` to wipe.** `reset_campaign()` doesn't touch every field, so anything it misses "survives" the round-trip by never having been erased. Under the weaker version, `max_acts`/`max_floors` appeared to persist despite not being in the save file at all.

The audit that produced this test found the chain otherwise sound — every field round-trips, defeat correctly calls `delete_saved_game()`, and victory saves before returning to the map. Its only other finding was two dead `static var`s (`total_enemies_override`, `boss_enabled`) with zero references project-wide despite sitting under a "Battle Configuration" heading; they're gone. Encounter size is set by `main.gd::start_game()` per `battle_type`.

#### Campaign structure: acts, floors, save files

A run is **12 acts, one Isaac-style floor each**, and a floor is a fixed 8-11 rooms (`FloorMap.ROOM_BASE/ROOM_PER_ACT/ROOM_MAX`). Length is bought with *act count*, not with bigger floors: each act ends in a boss room, a victory screen and a save point, so a longer campaign stays legible. The earlier `8 + (act-1)*2` capped at 22 made act 1 a 5-minute floor and act 8 a half-hour floor — two things that are supposed to be the same unit of progress. Combat rooms now sit at 5-8 per floor (8-12 minutes), because **a combat room here is not an Isaac room**: it is a full Battle City engagement (12-24 tanks, 4-6 concurrent, 2-3 s spawn interval), four to six times longer than Isaac's.

Only **3 unique visual themes** exist (Plains/Desert/Glacial), so acts 4+ lap back through them — `get_visual_act()` gives the theme (1-3), `get_difficulty_cycle()` the lap count (0-3 at 12 acts). Anything that varies by act must key off `get_visual_act()`, not the raw act number. Pushing past ~12 acts has sharply diminishing returns: encounter size grows +4/lap but `max_alive_for()` caps concurrency at 6 and `armor_plate_range()` caps the plate floor at 3, so laps saturate around the fourth.

**`current_floor` no longer means "which floor". It is `(act-1) × ACT_DIFFICULTY_STRIDE + rooms_cleared / 2`, clamped to `max_floors-1`.** The whole difficulty curve reads it (`main.gd::ENEMY_MIN_FLOOR`'s unlock thresholds, `enemy.gd`'s `FLOOR_SCALE_SLOPE` and `ARMOR_PLATE_FLOOR_GATE`, `MapTemplates.TEMPLATE_MIN_FLOOR`), and those curves are tuned over 0..14, so it keeps that range and only changes how it's computed.

**It must accumulate across acts, not reset per floor.** The reset version shipped first and silently locked out the back half of the game. Measured peak `current_floor` per act was 4 / 6 / 7 / 9 — against gates of **5** (AIRCRAFT, MIRAGE, BATTLESHIP, LASER, CRUSHER, SPLITTER — the entire "genuinely new counterplay" tier), **8** (MISSILE, WARP) and **9** (third armor plate). So act 1 could never roll any of those six, and acts 1-3 could never roll MISSILE/WARP or a tier-3 plate. Nothing errors; the roster just quietly looks thin. Fewer rooms per floor makes it worse, which is exactly the direction the design moved — hence `tools/test_floor_map.gd::_test_full_roster_unlocks_across_run()`, which asserts the *outcome* (every gated enemy and the top armour tier become reachable somewhere in a run) rather than any constant's value. Verified by reverting to the per-floor reset: it reports peak 6 and names MISSILE, WARP and the third plate.

Two more things it is deliberately **not**:

- Not BFS depth from the start room. Depth only reaches 6-8, and it *decreases* when the player backtracks through cleared rooms, so difficulty would oscillate.
- Not "rooms entered". Only `mark_room_cleared(key, count_progress=true)` advances it, and non-combat rooms pass `false`. Otherwise walking through a few shops would push the enemy tier up without the player firing a shot.

`rooms_cleared` is halved so the **act** dominates the curve. Undivided, the swing inside one floor (0..7) equals the swing across the whole campaign, so act 1's last room lands at act 8's first room and the curve sawtooths. Halved, a floor contributes a +0..3 ramp on top of an act-driven baseline. `ACT_DIFFICULTY_STRIDE = 1` is what makes 12 acts span exactly 0..14; the full roster finishes unlocking at act 6, tier-3 plates at act 7, and acts 8-12 lean on `get_difficulty_cycle()`.

Floor layout is generated by **`scripts/floor_map.gd`**, which replaced the Slay-the-Spire node graph (`_floor_band` / `_band_pool` / `_generate_spire_map` / `_ensure_shop_coverage` / `best_shop_route` are all gone). See "The floor is a room graph" below.

Two JSON saves under `user://`, deliberately independent:

- `campaign_save.json` — written by `save_campaign()`, called from `visit_room()` / `mark_room_cleared()` / `mark_secret_found()`. `load_campaign()` tolerates old formats (`_load_perk_dict()` accepts both the current `{perk_id: stacks}` dict and the pre-stacking `Array[String]`; a spire-era save has no `floor_rooms` and gets a freshly generated floor from `ensure_floor_ready()`).

  **`load_campaign()` must stay a pure deserializer.** The "no floor? generate one" repair lives in `ensure_floor_ready()`, called from `main.gd::start_game()`, *not* at the end of `load_campaign()`. It was written there first, and because `generate_floor()` resets `current_room` / `current_floor` / `battle_type` / `challenge_mode` / `floor_*_room`, a save whose `current_room` didn't match would have six fields silently overwritten one line after being read — `tools/test_persistence_roundtrip.gd` named all six. The repair also only *relocates* the player to the start room when rooms exist but `current_room` is stale; regenerating there would wipe every cleared-room flag, i.e. reloading a save would undo the floor's progress.
- `daily_challenge_save.json` — one seeded, single-life run per calendar day. `get_daily_seed()` hashes the date *plus a fixed salt* (raw date strings hash to near-sequential seeds). `main.gd::start_game()` calls `seed()` with it before generating map + enemies so everyone gets the same run.

#### The floor is a room graph (`scripts/floor_map.gd`)

A floor is a 9×9 grid of rooms, generated by the classic Isaac placement loop: BFS out from the centre cell, 50% chance per direction, and **reject any cell that already touches 2+ placed rooms**. That rejection rule is what produces a branching tree with occasional loops instead of a solid blob — and it is what guarantees dead ends exist, which is where every special room goes.

Doors are computed from adjacency (`_compute_doors`), never recorded during placement. Symmetry is therefore true by construction: there is no way to end up with a door on one side and a wall on the other. `tools/test_floor_map.gd` still asserts it across 200 seeds, because the *next* person may be tempted to hand-record them.

Things that are load-bearing and were each a real defect:

- **Both grid dimensions must be odd.** The start cell is `GRID/2` integer-divided, so a 9×8 grid puts the start at row 4 with four rows north and three south — measured over 600 floors, north/south room distribution came out 1.28 and the whole floor visibly grew upward. East/west was 1.06 in the same run because the column count was already odd, which is what identified the cause. 9×9 gives 1.01 / 0.98.
- **`_place_cells` refills the queue in rounds.** A single BFS wave with a 50% per-direction coin flip almost never reaches the target room count. The first version appended a reshuffled refill and then immediately `break`ed out of the loop, so the refill was never consumed — every floor was one wave, and hitting the target relied entirely on `generate()`'s 64-attempt outer retry. That "works", but each retry re-rolls the *whole floor* rather than completing the current one, throwing away almost all sampling.
- **Special rooms only go in dead ends**, and boss takes the deepest one. Putting them on through-routes means the player collects them incidentally; a dead end costs a detour, which is the decision the layout is there to create. Shops take the *shallowest* dead ends — build materials and upgrades are worthless if you first reach them next to the boss door.
- **The shop guarantee needs a fallback.** Shops are the only source of `structure_inventory` (`add_structure_stock()` is called from `shop_dialog.gd` and nowhere else), so a shopless floor half-disables the builder while looking like bad luck. Roughly 1 floor in 400 is near-enough a single loop that no dead end is left after boss/treasure; `_assign_types` then converts the shallowest through-route room instead. Flavour loss (no detour decision) beats a functional hole.
- **Secret rooms are placed last**, in the empty cell touching the most rooms, never adjacent to the boss (that would hand the player a shortcut past the fight). Their doors are marked `secret_doors` on **both** sides — a wall that is only cracked from one side reads as a bug from the other.

Room types map onto the old node types through `GameState.battle_type_for_room()`; `"normal"` → `"battle"` is the one non-identity entry, and anything that consumes `battle_type` (the `_request_spawn_enemy` roll tables, `encounter_size`, the balance probe's `NODE_TO_BATTLE`) needs that alias.

#### Doors, room transitions, and the base (`scripts/room_door.gd`)

**`RoomDoor.DOOR_COL = 3` / `DOOR_ROW = 6` — the vertical doors are deliberately off-centre.** The eagle and its five bricks occupy cols 5-7 × rows 11-12, so a south door at the edge midpoint (col 6) opens directly onto the eagle: the player cannot walk out, and cannot walk in. Cols 4 and 8 are the two player spawn cells, also reserved. Col 3 is the closest legal column to the centreline. The horizontal doors have no such conflict (the base is at rows 11-12, they sit at row 6), so only the vertical pair is offset — the asymmetry is forced by the base, not arbitrary. Both constants are global to every room, so an exit always lines up with the neighbour's entrance without any alignment logic. `tools/test_room_flow.gd` asserts the column avoids both reserved bands.

A door is two things at once, which is why it is its own node rather than a missing brick: a **collider** while locked (Isaac's door latch — you cannot leave a room you haven't cleared) and an **Area2D trigger** while open. They must never both be active, or the player triggers the transition and is simultaneously pushed back out of the doorway. The locked blocker joins `steel` **and** `border`, so explosives cannot blow an exit out of an uncleared room; the secret-room crack wall is a *separate* body joining `steel` only, so bombs and tier-3 plasma can breach it (reusing the existing destruction matrix rather than writing an eighth copy of the group ladder).

**The base is temporary and per-room.** It spawns only in an unfinished combat room and is removed by `_despawn_base()` the moment the room clears. That is not cosmetic: the eagle plus its brick ring is a solid 3×2 block across the bottom-centre, and leaving it in a finished room means a permanent obstacle that no longer has any gameplay purpose. Two consequences that are guarded:

- `trigger_shovel()` and the shovel-expiry branch in `_process()` must not rebuild it after the room is cleared, or a cleared room grows a fresh base and five steel walls out of nothing.
- `_clear_all()` must null `base_instance`. `queue_free()` is deferred, so for the rest of that frame `is_instance_valid(base_instance)` still returns true — and `enter_room()` builds the next room *in that same frame*. Left dangling, the shovel and the night-mode fog tracker both act on an eagle that is about to disappear.

**`_clear_all(keep_players = true)` on a room change.** The player tank must survive the transition or every door is a free full heal. Train carriages are **siblings** of the player (`player.gd::_sync_train_carriages()` uses `get_parent().add_child()`), not children, so they are preserved by the `player_carriage` group check — skipping only `p1_instance`/`p2_instance` decapitates the train at every door. After repositioning, `TrainFollowHelper.teleport_train_chain()` resets the follow history, otherwise the carriages fly across the room toward a trail that belongs to the previous one.

**Non-combat rooms must zero the encounter counters.** `total_enemies` / `enemies_spawned` / `enemies_alive` are `main.gd` members and survive room changes. Walking into a shop while they still hold the previous fight's values leaves stale numbers on the HUD, and because `_process()` tops up on `enemies_spawned < total_enemies`, a room that inherits a smaller `spawned` than the next room's `total` starts spawning tanks somewhere that should be quiet.

**Enemy spawning itself is unchanged.** Waves from the three top-edge spawn points, `spawn_timer` / `spawn_interval`, the `max_alive_cap` concurrency limit and `encounter_size(battle_type, cycle)` all behave exactly as before — every combat room is one full Battle City engagement. Room-ification changed *what happens after* a fight (doors open, base is removed), not how the fight is fed. `_begin_room_encounter()` only resets the counters, which used to be a once-per-battle job in `start_game()`.

**Booting `main.tscn` enters the start room, which is not a combat room.** So `GameState.battle_type` is rewritten to `"battle"` and `total_enemies` is 0 by the time `_ready()` returns. Any sampler that sets `GameState.battle_type` *before* instantiating the scene and then reads `total_enemies` off it — `tools/test_enemy_balance_curve.gd::_sample` and `tools/probe_balance_report.gd::_sample_floor` both did — silently samples the `battle` table with an encounter size of zero, which surfaces as "average HP 0.00" and reads like a balance collapse. Both now call a local `_force_room_battle_type(bt)` that rewrites the current room's type and re-enters through the real `enter_room()`.

#### The shop is a room, not a menu (`scripts/shop_stand.gd` / `shop_rerolder.gd`)

Buying is Isaac's: goods sit on **physical stands on the floor** with a price tag under each, and you buy by driving onto one. No modal, no buy button, no leave button (you walk out the door), no focus handling. What it replaced was a full-screen `PanelContainer` with 18 cards — a Slay-the-Spire shelf that left the tank parked behind a modal.

`shop_dialog.gd` survives as the **rules module**, not a screen: `build_inventory()` / `item_by_id()` / `can_buy_item()` / `apply_item_purchase()` are all static and UI-free, and the stands call them. `apply_item_purchase()` returns its message string instead of calling `_show_toast()`, which is what let the same function serve both a dialog toast and a battlefield HUD toast. The pool of 11 upgrades now lives in `_upgrade_pool()` as its single definition — `build_inventory()` draws 6 from it, `item_by_id()` looks up all 11. (First attempt had `_upgrade_pool()` call `build_inventory()`, which meant `item_by_id` could only find the 6 that happened to be drawn.)

- **Stock is stored on the room (`room["shop_stock"]`) and persisted.** Rooms are re-enterable, and the old `setup_shop()` re-shuffled on every call — measured: walking out and back in 6 times produced 6 completely different shelves, i.e. **a free reroll for the price of a walk**, which silently defeated the whole escalating `REROLL_BASE + REROLL_STEP × n` design. Under the spire graph a shop node was a one-shot visit so this couldn't happen. Only `{id, cost, sold}` is stored; icons and descriptions are looked up from `item_by_id()` at draw time so the save doesn't carry kilobytes of item text (and so editing a description doesn't desync old saves).
- **Reroll cost moved to `GameState.shop_reroll_cost`** for the same reason — it was an instance variable reset in `setup_shop()`, so re-entering the room reset it to 20 G.
- **Fixed 3 upgrades + 3 building supplies, not 6 random from the pooled 23.** Building supplies are the only source of `structure_inventory`, so folding them into one random pool means a floor that rolls no supplies half-disables the builder while reading to the player as bad luck. The dialog guaranteed this by listing all 12 every visit; a floor can't hold 12 stands, so the guarantee weakens to "3 of them, randomly chosen" — "this shop has no turret" becomes a real variable instead of a missing feature.
- **Nothing may sit on an entry point.** The reroll machine was first placed at cell (6,10), which is exactly `_place_players_at_entry()`'s default landing spot `(6.5, 10.5)` — so the first step into a shop room charged a reroll, and rebuilding the stands from inside a physics callback threw `Can't change this state while flushing queries`. There are five such points (four door-inner cells plus the default), and `tools/test_room_flow.gd` checks all five against every stand and the machine. Door corridors (`DOOR_COL` column, `DOOR_ROW` row) are excluded too, which is why the stand columns are 2/6/10 rather than 3/6/9.
- **`_on_shop_reroll()` defers its rebuild.** It is invoked from `body_entered`, i.e. during query flush; freeing and re-adding collision nodes there is rejected outright by the engine.
- **Purchases must sync `GameState` → `rpg_mgr` immediately.** Same scene now, so there is no scene change to do it implicitly — without `_sync_after_shop_purchase()` an upgrade bought mid-floor wouldn't take effect until the next act.
- Buying goes through `TrainFollowHelper.resolve_train_owner()`, so a train's carriages can't each trigger a sale as the tail sweeps over a stand.

#### Perks, branches, and structure stock

- **Perks are stackable**, stored as `{perk_id: count}` in `unlocked_perks` / `p2_unlocked_perks`, capped per-perk by `PERK_MAX_STACKS`. Perks with a numeric hook stack to 3 and scale via `RPGManager.get_perk_value()`; pass/fail mechanical gates stay at 1. A 15-floor run exhausted the old fixed pool of unique perks around floor 5-7, which is why stacking exists. Grant through `GameState.grant_perk_stack()` — `shop_dialog.gd` and `event_dialog.gd` write the persistent `GameState` layer directly and never assume a live `RPGManager`. That was originally because they lived in `spire_map.tscn`; now that they live on `main.tscn`'s HUD there *is* a live `rpg_mgr` in the same scene, so `main.gd::_on_room_dialog_closed()` pulls `sync_from_game_state()` when the dialog closes. Without that, a perk bought mid-floor wouldn't take effect until the next act — under the old flow the scene change did the sync for free.
- **Builder structures are shop-bought consumable stock**, not a gold cost at placement time. `GameState.structure_inventory` (`{structure_id: count}`) is bought from `shop_dialog.gd::BUILDING_ITEMS`, persists like gold/perks, and is spent by `builder_controller.gd` via `consume_structure_stock()`. `ui_theme_helper.gd`'s hotbar rebuilds itself from that dictionary and shows only structures with stock > 0, so any code changing stock must call `update_hotbar_stock()`.
- **Branch/tier is per player** (`tank_branch`/`branch_tier` vs `p2_branch`/`p2_branch_tier`); level/XP/gold and flat stat points are team-wide. Every `rpg_manager.gd` stat getter takes `player_id: int = 1`, and `upgrade_selection_dialog.gd` shows its picker once per player (`main.gd::pending_upgrade_players`) so P1/P2 can diverge. Branches are `"default"`/`"speed"`/`"heavy"`/`"train"`; `"train"` makes `player.gd` attach follower `train_carriage.gd` instances (`_sync_train_carriages()`) that trail and fire independently, and `enemy.gd`'s TRAIN_BOSS reuses the same scene with `is_enemy = true`.
- **Beware the "star tier" trap** documented in `grant_star_tier_reward()`: `player_tier` only has an observable effect on the `"default"` branch, and every player picks a branch at their first level-up. Rewards that "raise your tier" redirect to `+1 atk_bonus` for branched players.
- **Any reward granted outside a battle has to ask "which players?"** Most shop/event rewards write team-wide `GameState` fields (`max_hp_lvl`, `fire_rate_lvl`, `speed_lvl`, `builder_lvl`, `atk_bonus`, `player_xp`) and both players get them for free. Exactly four do not: **lives** (`player_lives` vs `p2_lives`), **star tier** (`player_tier` vs `p2_tier`), and the three shop perks — because perks live in `unlocked_perks` vs `p2_unlocked_perks`. `event_dialog.gd` had this right (`_grant_life` / `_grant_tier_up` / `_grant_perk` all fan out on `player_count == 2`); `shop_dialog.gd` hardcoded `player_id = 1` for all four, so in 2-player co-op **P2 could never receive them** — gold was still deducted and the success toast still fired. Use `_reward_targets()` there. `tools/test_shop_economy_2p.gd` asserts shop and event agree on the same reward, and was verified to report all four against the pre-fix code.
- **Cap checks must live in the buy path, not only on the button.** `_can_buy_item()` was enforced solely via `btn_buy.disabled`. A disabled Button emits no `pressed`, so the UI was safe — but `_on_buy_item()` itself deducted gold and then called `grant_perk_stack()`, which silently returns `false` at cap. One new caller away from "charged full price, granted nothing, showed a success toast", with nothing logged. The guard is now in both places.

### Cross-node coupling

Actors reach the battle controller via `get_tree().current_scene` and duck-type it (`main.rpg_mgr`, `main.has_method("trigger_bomb")`, `main.actors_container`). `player.gd`, `enemy.gd`, and `builder_controller.gd` all assume the current scene is `main.tscn`; running those scenes standalone degrades rather than crashes (null-guarded), but stats won't apply.

**`GameArea` sits at `position = Vector2(48, 48)`, so local and global coordinates differ by exactly one tile.** Every container the game spawns into (`MapContainer`, `ActorsContainer`, `BuilderController`) lives under it, and the grid maths in `_build_map()` (`(c + 0.5) * TILE_SIZE`) produces **local** coordinates. Mixing the two is silent — nothing errors, the thing just renders or lands one tile up-left. Three shipped bugs came from exactly this:

- `laser_piercer.gd::_spawn_laser_visual()` set `beam_spr.position` (local) from a global midpoint, so the beam drew a tile away from where the raycast actually hit — while the muzzle flash and shockwave, which go through `VFXAnimator` (global, all three call sites), stayed correct.
- `get_random_empty_tile_position()` returned local coordinates but `wormhole.gd` assigned them to `body.global_position`. Measured over 200 samples: 54 landed inside brick, 7 on another solid type, 24 outside the map. It now returns **global** (`map_container.to_global(...)`) and both call sites use `global_position`.
- `oil_barrel.gd::detonate()` set `exp_inst.global_position` *before* `add_child()`, so the fireball drew one tile down-right of the barrel while the shockwave/debris/dust (via `VFXAnimator`) and the `intersect_shape` kill radius all stayed correct — the visual blast centre and the actual kill zone disagreed by a full tile. Every other explosion spawn site (`landmine`, `bullet`, `base_eagle`, `defense_turret`, `fortified_wall`) already had the right order; this was the lone inversion. `tools/test_oil_barrel_blast.gd` covers it.

Rule of thumb: spawning a *tile* into `MapContainer` at grid coordinates → `.position`. Anything positioned from a world-space value (a raycast hit, another node's `global_position`, a teleport target) → `add_child()` **first**, then `.global_position`. Setting `global_position` before the node is in the tree silently behaves like `position`.

**Corollary: `_ready()` runs *during* `add_child()`, i.e. one step before the caller assigns the position.** So a spawned node's `_ready()` must never read its own `global_position` — it sees the parent's origin, not where it is about to be placed. `explosion.gd` did exactly this to light up the night-mode fog, and since its parent is `ActorsContainer` under `GameArea`, subtracting `game_area.global_position` cancelled out perfectly and *every* explosion in the game flashed the map's top-left cell `(0,0)`. It was invisible outside `night_ops` / `night_bombs`, and it affected all six explosion spawners, not just the barrel. The fix is `call_deferred()` — deferred calls run after the current call stack unwinds, by which point the caller has assigned the coordinate. `tools/test_oil_barrel_blast.gd` asserts the flash lands on the blast, and was verified to report `(0.0, 0.0)` against the pre-fix code.

**A teleport is not visible to shape/ray queries until the next physics step.** Assigning `global_position` updates the node transform immediately, but the physics server's broadphase only picks it up when it next flushes — so any `intersect_shape` / `intersect_ray` running in that same frame still sees the body at its **old** location. This bit `test_flamethrower.gd`: the test teleported the player behind the tank and asserted no damage, but the flame's first damage tick queried a stale broadphase that still had the player standing in front, so "the cone hits backwards" was reported for a cone that is actually correct. The fix is to let one or two physics frames elapse after any teleport before querying. It matters outside tests too — anything that teleports a body (`wormhole.gd`, `TrainFollowHelper.teleport_train_chain()`) and then immediately raycasts from or toward it is reading pre-teleport geometry.

`main.gd` (~2000 lines) builds the battlefield entirely in code — the 13×13 grid comes from an int array of **tile types 0-30**, tiles are `StaticBody2D`s or scene instances created at runtime, and `main.tscn` only contains empty containers: `GameArea/{MapContainer, BaseWallContainer, ActorsContainer, BuilderController}` plus the `HUD` CanvasLayer. `TILE_SIZE = 48.0`.

**The tile-type legend lives at the top of `scripts/map_templates.gd`** — keep it in sync when adding a type; it's the only place all 31 are described. The dispatch chain is `main.gd::_build_map()`'s `if tile_type == N` ladder (~line 466). Types beyond the classic terrain (0-9) instantiate behaviour scenes rather than plain tiles: moving platforms, wormholes, shield stations, wind blowers, conveyors, jump pads, street lamps, electric walls, oil barrels, signal jammer towers, factories, drifting supplies, enemy shield towers.

Layouts come from two sources, both behind `MapTemplates.get_layout_for_stage(floor_idx, battle_type, act, allow_procgen)`:

- **Hand-authored templates** in `map_templates.gd` (`TEMPLATE_CLASSIC`, `TEMPLATE_RIVERS`, `TEMPLATE_DESERT_STORM`, …), selected by cycled visual act + battle type.

  **Map choice is shuffled per run, but the shuffle must not break the sweep.** `_pick_from_pool()` used a bare `floor_idx % eligible.size()` — fully deterministic, so *every run showed the same maps in the same order*: act 1 was always MEADOW_OUTPOST, CLASSIC, procgen, ORCHARD_ROWS, … and only 8–10 of the templates (56 as of now) were ever reachable. It now offsets by `GameState.run_seed` (persisted in the save, so reloading or re-entering a floor keeps the same map; `0` means an old save and falls back to the legacy behaviour). The offset uses a per-run **start + stride coprime with the pool size**, not a per-floor hash: a per-floor hash is independent uniform sampling and collides inside a single run (one seed drew ORCHARD_ROWS three times in 15 floors), whereas a coprime stride still walks the whole pool without repeats. Measured across 20 runs this took act 1 from 8–10 distinct templates to 18, act 3 to 22.

  A consequence: "template X appears on floor N" is no longer true of any single run, so `test_map_templates_and_base_fit.gd` asserts the *actual* invariants instead — every entry map is reachable across several seeds (the original dead-index bug), and floors 0–1 draw only entry-tier maps in every seed.

  **Pool order is load-bearing — appending a template to a pool usually means it is never selected.** The gating below still applies on top of the shuffle. `eligible` grows with the floor (floor 0–1 sees only ungated templates, floor 2 adds the `min_floor=2` ones, floor 5 the rest). Combined with `floor_idx % 3 == 2` diverting to procgen, a 15-floor act only ever consults templates on floors 0,1,3,4,6,7,9,10,12,13 — i.e. a fixed handful of indices. Four new entry maps appended to the end of `act1_pool` landed at indices 14–17 and were dead code: reachable only at floors 14 and 17, both of which are procgen floors. Place a new template where the gate tier you want can actually reach it, and confirm with `test_map_templates_and_base_fit.gd`, which asserts every entry map is drawn at least once across several run seeds.

  Gating a template is not optional bookkeeping: `TEMPLATE_SOLAR_TITAN_SANCTUM` was left out of `TEMPLATE_MIN_FLOOR` on the stated grounds that it is "only a fixed `battle_type=="boss"` return, not pool-indexed" — but it also sits in `act3_pool`, and defaulting to `min_floor=0` made it the pool's *only* floor-0-eligible entry. Act 3 therefore opened with the game's densest map (8 mechanic families) twice in a row, against 0 families for acts 1 and 2. That is the same "hardest map comes first" failure `MapDirector` was built to fix, mirrored on the template side.

  Templates carry hard structural requirements, all enforced by that test: 13×13; `[11][5..7]` and `[12][5,6,7]` empty because `main.gd::_spawn_base_and_walls()` puts the eagle and its five brick walls there itself; `[12][4]`/`[12][8]` empty for player spawns; `[0][0]`, `[0][6]`, `[0][12]` empty for enemy spawns. The test enumerates templates via `get_script_constant_map()` rather than a hand-written list — the previous hardcoded list covered 36 while the file had grown to 50, so every template added after it was silently unchecked.
- **`map_generator.gd` + `map_director.gd`** — procedural 13×13 generation, used on every `floor_idx % 3 == 2` regular battle floor and for the whole Daily Challenge map. The two are deliberately split: `map_generator.gd` is only a **sampler** (fill the grid from a plan — `generate_planned()`; the old `generate_map()` signature remains but routes through the same path rather than being a second implementation), while `map_director.gd` decides the plan, validates the result, and repairs or re-rolls it. It builds one half by weighted rolls, mirrors it (`HORIZONTAL` mirroring also flips directional conveyor/wind tiles), then `_carve_critical_paths()` force-clears spawn zones and the eagle sanctuary. Any new directional tile type must be added to `_mirror_tile_horizontal()`/`_mirror_tile_rotational()` or mirrored maps will point it the wrong way. The old `_sprinkle_tactical_features()` is gone — fixed shield-station/lamp/wormhole placements are now expressed as mechanic *families* in the director's per-tier budget instead of being stamped onto every map.

**Trees conceal, but must not erase.** `tile_trees` is the one terrain drawn *above* actors (`z_index = 10`, a bare `Sprite2D` with no collision) and it is 100% opaque, so a tank driving in used to vanish completely — you could not tell whether enemies were in a thicket, or where your own tank was. `main.gd::_update_tree_transparency()` fades only the cells a tank currently overlaps to `TREE_REVEAL_ALPHA` (0.38). Three things it deliberately does:

- It iterates **tanks, not tiles**, so cost is independent of how much forest a map has.
- It uses the tank's **bounding box, not its centre cell** — tanks are ~40px against 48px tiles, so straddling two cells is the normal case, and the half of the tank poking into the next cell is exactly the half you need to see.
- It **skips a camouflaged MIRAGE**. That enemy disguises itself as a tree tile when it holds still; if the real trees around it faded, the fade would mark its position on the map and the whole mechanic would be dead. A stealth unit must not give itself away.

The alpha is deliberately not 0: concealment is the entire tactical point of the tile, so the reveal shows a silhouette and rough position, not facing or health. `main.gd` must call `tree_sprites.clear()` in `_clear_all()` or the dictionary keeps freed sprites across floors.

**Gold/yellow is enemy vocabulary, not terrain decoration.** `enemy_power`/`enemy_armor`/`enemy_basic` all carry gold trim (see the `ENEMY_PALETTES` comment), and `enemy_basic` was recoloured violet specifically so it separates from the lavender-grey steel wall. `tile_steel` used to wear a radius-0.75 gold insignia — the largest gold surface in the game, i.e. terrain dressed as an enemy, and measurably over-dominant (centre-vs-whole colour deviation 51, against 1–14 for every other tile; tiled, it read as polka dots rather than steel). It is now a darkened steel boss, separated by *value* rather than hue, with the rivets moved onto the frame edges so four tiles' quarter-rivets compose into one rivet per grid vertex. The plate was darkened at the same time because the gold had been doing double duty: it was also what told steel apart from the similarly-light `tile_ice`, so that job had to be handed to luminance.

World sprites are **256×256** renders drawn at `TILE_SCALE = TILE_SIZE / 256.0` (0.1875); the same 0.1875 is hardcoded in most `scenes/*.tscn` sprite nodes, so changing the render resolution means updating every one of them.

### Texture loading and the mipmap situation

`TextureHelper.get_tex(path)` (`scripts/texture_helper.gd`) is a static cache: it tries `load()` first, and only falls back to `Image.load_from_file()` + `generate_mipmaps()` when `ResourceLoader.exists()` is false. Scenes carry no `ext_resource` texture references — every sprite swap (tank tiers, water frames, node icons) is a string-path lookup, so **naming conventions are load-bearing**.

That 5.33× minification needs mipmaps to stay clean (nearest/unmipmapped sampling at this ratio produces crawling aliasing, not pixel-art chunkiness), paired with `textures/canvas_textures/default_texture_filter=3` (Linear Mipmap) in `project.godot`.

**This guarantee was inert for a long stretch and is now enforced by a test.** `.import` files were committed for all ~430 sprites as of v0.06316, every one with `mipmaps/generate=false`. Because an `.import` file makes `load()` succeed, `TextureHelper`'s `generate_mipmaps()` fallback never ran — so the pipeline's central assumption held nowhere, and nothing errored, because a texture without mipmaps renders fine, just aliased. All 453 texture `.import` files were flipped to `mipmaps/generate=true` and reimported; `tools/test_texture_mipmaps.gd` now loads every PNG under `res://assets/sprites` and asserts `get_image().has_mipmaps()`, plus asserts `default_texture_filter` is still a mipmap tier. Both halves matter — turning off either one silently restores the old behaviour. Note the `TextureHelper` fallback stays inert by design now; mipmaps come from the importer, not from runtime generation, which is also the only way they survive an export (`Image.load_from_file()` cannot read a `res://` PNG in a packed build).

After adding sprites, run `godot --headless --path . --import` and then that test; the `.import` file Godot writes for a new PNG defaults to `mipmaps/generate=false`. This is not hypothetical — the three `enemy_plate_t*.png` added later landed with mipmaps off and had to be flipped by hand before `test_texture_mipmaps.gd` would pass. Since then the hand-flipping has been scripted per batch: `tools/generate_new_imports.py` (tanks), `tools/generate_splitter_imports.py`, `tools/generate_enemy_shield_tower_imports.py` (buildings) each write `.import` files from a `mipmaps/generate=true` template for one sprite directory. They are batch-specific by directory, not general — copy one and change `source_file`/the filename list rather than assuming an existing one covers your folder. Current state is clean: all 509 PNGs (plus 7 SVGs) under `assets/sprites` have an `.import`, and none of them says `mipmaps/generate=false`.

Sprite naming, which now mixes two schemes:

- **Enemies**: `enemy_{basic,fast,power,armor,missile,laser,boss,desert,bomber,suicide,mirage,battleship,aircraft,warp,flame,crusher,sniper,gatling,shotgun,splitter,split_mini,engineer,spider}[_bonus]_f{0..5}.png` — **6 frames**, same as players (they were 2-frame historically). Plus `enemy_plate_t{1,2,3}.png`, single-frame armor-tier overlays drawn on top of *any* enemy type (one set for all 24 types, rather than 24 × 6 × 3 = 432 per-type variants).
- **Players**: 6-frame, prefixed by both player slot and branch (`player.gd::_update_tier_appearance()`): `{player|player2}_tier{0-3}` for the default branch, or `{player|player2}_{speed|heavy}_t{1,2}` / `{player|player2}_train_loco_t{1,2}` once a branch is picked. `player2` means P2's tank, not a tier — there is no shared or recoloured sprite between P1 and P2.

### Enemies: variety gated by floor, not stat inflation

`enemy.gd::EnemyType` has 28 members. Which ones can appear is governed by `main.gd::ENEMY_MIN_FLOOR`, grouped by *mechanic* rather than raw stats — floor 1 unlocks reskins of the direct-fire loop (POWER/SUICIDE/ARMOR), floor 2 adds close-range burst (SHOTGUN) and camouflage ambush (HUNTER), floor 3 adds area denial (BOMBER's delayed AoE, FLAMETHROWER's sustained forward cone), hazard trails (FIREWALL), and field construction (ENGINEER's 10s building cycle), floor 4 adds high-contrast archetypes (SNIPER's railgun, GATLING's heavy suppression stream, SPIDER's jump-over-obstacles mobility, SANDWORM's underground burrowing ambush, and CANNON's close-range deployment into a high-defense stationary siege fortress), floor 5 adds genuinely new counterplay (AIRCRAFT ignores all terrain, MIRAGE cloaks, BATTLESHIP/LASER hit in AoE/pierce lines, CRUSHER smashes through all steel and structures), floor 6 adds colony/split mechanics (SPLITTER heavy mother tank, splitting into 4 agile SPLIT_MINI drones on death), floor 8 adds the boss-adjacent tier (MISSILE/WARP). `_gate_enemy_type()` downgrades anything spawned too early.

FLAMETHROWER is the one enemy whose weapon is a *persistent* node rather than a per-shot call: `scripts/flame_jet.gd` is a `Node2D` parented to the tank, so the cone inherits the tank's transform and never needs per-frame coordinate syncing — which is also why it sidesteps the local-vs-global trap described above. It bypasses `fire_timer` entirely and runs its own burn/rest cycle (`FLAME_BURN_TIME` / `FLAME_REST_TIME` in `enemy.gd`); the rest window is the counterplay, and the always-lit pilot flame on the nozzle sprite is its visual tell. Range is deliberately short (132px, 2.75 tiles) so flanking beats it — lengthen that and it stops being a positioning puzzle and becomes a stat check. Its `_physics_process` branch must **not** `return` early: everything below it is movement, so an early return turns the tank into scenery (`test_flamethrower.gd` asserts this).

One **act-themed "signature" enemy** slot signals which act you're in by silhouette: Act 1 → ARMOR (the default filler), Act 2 → DESERT, Act 3 → WARP, keyed off `get_visual_act()`. Daily Challenge deliberately bypasses the gate entirely and rolls uniformly across the full roster.

**Enemy strength can also come from the map, not the roster: the Enemy Shield Tower (tile type 30).** `scripts/buildings/enemy_shield_tower.gd` is an 8 HP destructible hostile structure that grants every enemy inside a 180 px `Area2D` an invulnerable shield, and it is the only enemy buff that is a *placeable object* rather than a stat on the tank. It fits the "integer and visible" rule below by construction — the buff has a location you can see, and the counterplay is to shoot the tower rather than to out-DPS a hidden multiplier. Two implementation points: the buff is **reference-counted on the enemy** (`add_shield_source(self)` / `remove_shield_source(self)`), so overlapping towers stack and leaving one radius does not strip a shield the other still provides; and `_destroy()` must walk `shielded_enemies` and release every source before `queue_free()`, or the survivors keep a shield with no tower left to shoot. `tools/test_enemy_shield_tower.gd` covers the protect/dispel cycle and the encyclopedia entry.

### Encyclopedia / Tactical Compendium (`scripts/encyclopedia_data.gd` & `scripts/encyclopedia_dialog.gd`)

The Tactical Compendium (战术图鉴百科) is accessible directly from the Title Screen via `COMPENDIUM (战术图鉴百科)`. It features a two-pane layout with 5 major categories:
- **UPGRADES (升级路线树)**: 4 Specialization Trees (Classic, Speed, Heavy, Train), 7 Passive Tactical Perks (Rapid Loader, Titan Plating, Nitro Booster, Ricochet Rounds, Amphibious Hull, Nano Repair, High Explosive), and Level Progression Curves.
- **TANKS (坦克战车)**: Player tank branches (Classic, Speed, Heavy, Train) and all 24 enemy types with full combat stats, mechanics, and counterplay tips.
- **ITEMS (道具宝物)**: Core power-ups (Star, Bomb, Clock, Helmet, Shovel, Life) and battle loot (Gems, Keys, Chests, Supplies).
- **BUILDINGS (防御建筑)**: Deployable defense structures (Turrets, Electric Walls, Repair Stations, Shield Stations, Wind Turbines, Street Lamps, Oil Barrels, Roller Walls, etc.).
- **TERRAIN (战场地形)**: Environmental and hazard tiles (Brick, Steel, Forest Trees, River Water, Sand Dunes, Ice, Hard Clay, Conveyors, Jump Pads, Wormholes, and Base Eagle).

All entries are strictly typed, contain high-resolution sprite icons, and integrate seamlessly with gamepad/keyboard navigation via `UIThemeHelper.focus_first()`. Automated coverage is enforced via `tools/test_encyclopedia.gd`.

#### Enemy toughness is integer and visible — armor plates, never a multiplier

This is Battle City, not an RPG. **Enemy strength may only change in whole numbers, and every increment must be something the player can see.** In Tank 1990 the armored tank takes four hits *and looks different*; that's the contract.

`max_health = base_health + armor_plates × ARMOR_PLATE_HP`, where `armor_plates` ∈ 0–3 and each level has its own overlay sprite (`enemy_plate_t1/t2/t3.png`, rendered by `tools/build_armor_plating.py`). Integer addition — no `ceil()`, no float anywhere in the health path.

This replaced `max_health = ceil(base × (1 + floor × 0.08))` plus a stack of `× 1.5` / `× 1.6` / `× 1.18` multipliers for elite / boss / difficulty lap. That version was invisible by construction: a floor-12 `enemy_basic` had 3 HP and was pixel-identical to the floor-0 one, so a player who fired twice and saw it survive learned nothing except "this game inflates numbers behind my back".

Design points that are easy to get wrong:

- **Don't add HP to everything — spawn *plated variants*.** Blanket additive armor destroys type identity: BASIC at +6 is a 7 HP brick, and "trash dies in one shot" is the floor of the whole genre. Instead, floor raises the **upper** bound of the plate roll, so a late floor fields a *mix* of bare and plated tanks and the player can see at a glance which ones to route around. Elite / boss / difficulty lap raise the **lower** bound (`elite` +1, `boss` +2, `+cycle` per lap) — "this fight has no bare tanks in it" is itself a readable statement.
- **Both bounds clamp to `MAX_ARMOR_PLATES`.** There must never be HP without a matching sprite — that's the old hidden multiplier sneaking back in. `tools/test_armor_plating.gd` asserts this over every (floor × battle_type × cycle) combination, and separately asserts that a plated tank actually has a `plate_sprite` child at runtime, since getting the count right but failing to attach the art is indistinguishable from a hidden stat.
- **Consequence: high floors saturate.** Once the floor gates max the upper bound, elite/boss/lap can only push the lower bound toward 3, so acts 4–8 gain little HP. That's intended — late difficulty is meant to come from composition, count, and mechanics, per this section's heading.
- **The overlay is a child of `Sprite2D`, not of the tank.** Scale, rotation, fire recoil, and hit-squash then all propagate for free; nothing needs per-frame syncing. It is also **hidden while a MIRAGE is camouflaged** — plating visible on a "tree" would mark the unit's position and kill the mechanic, the same reason `_update_tree_transparency()` skips camouflaged MIRAGEs.
- **Plate tiers read by coverage first, value second — never by hue.** World sprites are drawn at `TILE_SCALE` 0.1875 (256 px → 48 px), where the only reliable signals are silhouette size and luminance. Tiers grow 4.7% → 7.7% → 13.3% alpha coverage and darken 138 → 103 → 72; `test_armor_plating.gd` asserts both are monotonic. Gold/yellow is deliberately avoided because it is already *enemy type* vocabulary (see the `tile_steel` note below) — two meanings on one channel is how you make both unreadable.

The line this draws, which the remaining multipliers sit on the right side of: **strength quantities (HP, damage) must be integer and visible; rates and timings may scale continuously.** Elite/boss `fire_interval × 0.85`/`× 0.80` stays — bullet density is something you feel immediately, and elite/boss fights announce themselves anyway. Rewards (`xp`/`gold`/`score` × 1.5–1.8) stay because they're printed on the results screen, i.e. already visible.

`speed × 1.08` (elite/boss) and `speed × (1 + cycle × 0.07)` (per lap) were **deleted**. 75 → 81 px/s crosses a 48 px tile in 0.59 s instead of 0.64 s: not perceptible, not readable, hidden — the worst of both. The difficulty those carried moved to two integer, visible levers in `main.gd`:

- **`encounter_size()`** — `+4` tanks per completed lap (12/16/20 for a regular battle). "This fight sent 20 instead of 12" is legible in a way that 7% more speed never is.
- **`max_alive_for()`** — the concurrent-enemy cap, `4 → 5 → 6` by lap, capped at 6. This one is load-bearing: the cap was a hardcoded `enemies_alive < 4`, so raising `encounter_size` alone only made laps **longer**, not harder — same pressure at every instant, just more of it. Two extra tanks on screen is the actual Battle City difficulty lever. 6 is the ceiling because a 13×13 map with three spawn points starts jamming its own reinforcements beyond that, which plays *easier*.

`tools/test_enemy_balance_curve.gd::_check_lap_ramp()` asserts each lap's encounter HP (`encounter_size × avg_hp`) exceeds the previous by 10%; measured 85 → 114 → 163 (×1.92 overall). It's an *outcome* gate, satisfied by either lever — which is the point, since the failure it guards against is "someone deleted a hidden multiplier and forgot to replace the difficulty". Verified: zeroing both `ENCOUNTER_PER_LAP` and the cycle term in `armor_plate_range()` makes it report 82 → 77 → 71.

### Collision layers and groups

**Collision layers are almost unused — do not design against them.** Layers are unnamed in `project.godot`, and `player.tscn`, `enemy.tscn`, `bullet.tscn`, `base_eagle.tscn`, `power_up.tscn`, every `scenes/buildings/*.tscn`, and every runtime-created tile all keep Godot's defaults (layer 1, mask 1). Everything collides with everything and is then filtered by group name in the callback.

The only explicit assignments in the whole project:

| where | layer / mask |
|---|---|
| `scenes/moving_platform.tscn` | layer 16, mask 3 |
| `scenes/wormhole.tscn` | layer 16, mask 15 |
| `train_carriage.gd` (enemy carriage) | layer 2, mask `1\|4\|16` |
| `train_carriage.gd` (player carriage) | layer 1, mask `2\|4\|16` |
| `enemy.gd` AIRCRAFT | mask 16 — flies over all terrain |

Plus raycast query masks: `laser_piercer.gd` and both landmine scripts use `1\|2\|16`, `builder_controller.gd`'s placement check uses `1\|16`. Those queries are where the intended bit semantics survive (1 = terrain/players/eagle/buildings, 2 = enemies, 4 = bullets, 16 = buildings/platforms/wormholes) — but since nothing outside the table above actually *sets* those layers, a mask of `1|2|16` in practice just means "hit layer 1, i.e. nearly everything, plus platforms/wormholes."

**Dispatch is by group name.** Core: `player`, `p1`, `p2`, `enemies`, `brick`, `steel`, `water`, `border`, `base_eagle`, `buildings`, `powerups`, `collectibles`. Terrain/mechanic groups added since: `hard_clay`, `sand`, `sand_dune`, `ice`, `landmines`, `hazard`/`hazards`, `conveyor`, `wind_blower`, `jump_pad`, `wormholes`, `shield_station`, `street_lamp`, `electric_wall`, `oil_barrel`, `signal_jammer`, `factory`, `drifting_supplies`, `roller_wall`, `treasure_chest`, `treasure_key`, `diamond_gem`, `timed_bomb`, `player_carriage`, plus the umbrella `terrain` / `obstacle` / `destructible`.

Room doors add three more: `room_doors` (the `RoomDoor` node itself), `room_door_blocker` (its locked collider — also `steel` + `border`, so nothing can blow an exit out of an uncleared room) and `secret_door_wall` (the crack wall — `steel` but deliberately **not** `border`, so explosives and tier-3 plasma can breach it). The two are separate bodies precisely because one must be indestructible and the other must not. Shop furniture adds `shop_stand` and `shop_rerolder`; both are `Area2D` triggers with no collision layer, so tanks and bullets pass straight over them.

**`enemy_building` is the newest axis, and nothing else in the codebase reads it yet.** `scripts/buildings/enemy_shield_tower.gd` (tile type 30) joins `building` + `buildings` + `enemy_building` + `enemy_shield_tower`, and it is the first *hostile* structure — every other member of `buildings` is player-placed or neutral furniture. Everything that dispatches on the umbrella group therefore treats it as friendly infrastructure, and two call sites already show what that costs:

- `enemy.gd`'s CRUSHER melee branch smashes anything in `buildings` via a `destroy`/`detonate`/`take_damage(999)`/`take_hit(99)`/`queue_free()` cascade — so a CRUSHER that drives into its own faction's shield tower deletes it.
- `repair_station.gd` heals every `buildings` member in radius, i.e. a *player* station would repair the enemy tower. It doesn't, but only by accident: the guard is `has_method("heal")` and the tower happens not to define one. Adding a `heal()` to it later silently turns that on.

When you add faction-sensitive behaviour, branch on `enemy_building` explicitly rather than assuming `buildings` means "ours".

**`player` is not the same set as "the player tank".** `train_carriage.gd::_ready()` puts follower carriages in the `player` group, and it has to — enemy fire and damage checks find targets by that group. The consequence is that *every* pickup gated on `is_in_group("player")` fires for a carriage. Most collectibles don't care, because they credit a team-wide account on `get_tree().current_scene` (`gold_coin`, `diamond_gem`, `drifting_supplies`, `treasure_chest`, `treasure_key` all do). Two did care:

- `power_up.gd` called `apply_powerup()` **on the body**. A carriage has no such method, so the old `if body.has_method(...)` guard skipped the effect but still played the sound and `queue_free()`d the pickup — the train ate its own power-ups with its tail, silently, more often the longer the chain.
- `gold_coin.gd` / `diamond_gem.gd` read `body.player_id` to scale the `magnetic_salvage` perk; a carriage has no `player_id`, so the bonus vanished on any coin the tail happened to touch.

Both now go through `TrainFollowHelper.resolve_train_owner(body)`, which walks `leader_node` (which may chain carriage→carriage) up to whatever actually has `apply_powerup`, and returns `null` for bodies that aren't part of a train at all — so a non-train body leaves the pickup on the ground instead of consuming it. It has a hard iteration cap so a cyclic `leader_node` can't hang the frame. `tools/test_train_pickup.gd` covers the chain, the null cases, and the cycle guard with duck-typed stubs (no battle scene needed, same idea as `tools/_train_stub.gd`).

Watch for **singular/plural group drift**: `enemy.tscn` declares `enemy` but `enemy.gd::_ready()` adds `enemies` (so `bullet.gd:147` checks both); `base_eagle.tscn` declares `base` while the script adds `base_eagle`; buildings variously add `building`, `buildings`, or both. When adding a group check, check both spellings or you'll silently miss half the cases.

The flip side is **checks against groups that don't exist at all**, which read as implemented behaviour but are dead branches. `oil_barrel.gd` tested `is_in_group("trees")` in its 3×3 blast, implying barrels clear foliage — but tree tiles are a bare `Sprite2D` with no collision body and no group (see "Trees conceal, but must not erase"), so they never appear in an `intersect_shape` result and never could. That check is gone; giving trees a collider to "fix" it would turn cover into a wall and kill the MIRAGE disguise. Two harmless ones remain on purpose: `is_in_group("train_carriage")` (`wind_blower.gd`, `conveyor_belt.gd`) and `is_in_group("bullets")` (`wormhole.gd`) name groups nothing adds, but each is `or`-ed with a check that does match (`body is CharacterBody2D`, `is_in_group("bullet")`), so behaviour is correct and the redundancy is defensive.

`bullet.gd::_on_body_entered` is the single place terrain destruction is decided (`brick` always breaks; `steel` breaks only for tier-3 plasma bullets and never for `border`). The property that actually gates this is `bullet.gd::can_destroy_steel` — grep for that, not for "tier 3"; the newer tests call the same thing a "Stage 2 shell" (`tools/test_roller_wall_and_stage2_destruction.gd`), so all three names refer to one flag. Walled structures (`defense_turret`, `fortified_wall`, `electric_wall`) join `steel` on top of `buildings`, so bullets treat them as indestructible steel; soft ones (`factory`, `shield_station`, `signal_jammer_tower`) don't, and take damage instead. `hard_clay_block.gd` joins **both** `brick` and `hard_clay`: bullets route it through the `brick` branch but call `take_hit(damage)` instead of freeing it when the target `has_method("take_hit")`, letting it absorb 3 hits with a colour-stage flash. `laser_piercer.gd` (a stateless `RefCounted`, called from `player.gd`/`enemy.gd` weapon tiers) re-implements the same group checks along a raycast line rather than reusing `bullet.gd`, since a pierce beam damages many bodies per shot instead of dying on the first. Adding a terrain or structure kind means adding its group here — and to `laser_piercer.gd` if it should also block/be hit by beams.

**Bullets are one path; explosives are four more, and they drifted apart.** `timed_bomb.gd`, `missile_strike.gd`, `buildings/oil_barrel.gd` and `buildings/landmine.gd` each carry their own terrain rules. A player reported "bombs can't destroy the white bricks" (`tile_steel`, the palest wall), and the cause was that only the **landmine** destroyed steel — so a 40 G mine breached walls a 60 G timed bomb and a 90 G missile strike could not. Steel is now breakable by all four (the tile legend in `map_templates.gd` says so; bullets still need tier-3 plasma). `tools/test_explosive_terrain_matrix.gd` prints the full 4 × 4 matrix and asserts **consistency** rather than any specific cell — the cell values are a design call, four implementations disagreeing is not.

Two things that matrix has to keep pinning down:

- **`border` must survive everything.** The map's edge walls are in the `steel` group too, so "let explosives break steel" naturally breaks the map open and lets tanks drive off it — silently, with no error. Every one of the four has to remember `not is_in_group("border")` on its own.
- **`sand_dune` and `hard_clay_block` are in the `brick` group as well**, so whichever `brick` branch runs first decides their fate. All four explosives currently one-shot hard clay; that's intended (its multi-hit HP is meant to resist *bullets*, and `timed_bomb`/`missile_strike` say `take_hit(99)` explicitly) but three of them get there by `queue_free()` via the brick branch rather than through `take_hit`, so a future change to hard clay's HP or loot rules would silently bypass them.

**And a sixth path that is not a projectile at all: `buildings/roller_wall.gd`.** It is the one structure that *relocates*, and it destroys terrain by arriving on it. `bullet.gd` duck-types `take_hit_direction(damage, dir)` (both the body and the area branch), which snaps the wall exactly one 48 px cell along the dominant cardinal of the bullet's travel direction — so the player aims the wall by choosing which side to shoot. Before moving it runs its own `intersect_shape` at the destination with mask `1|2|16` and resolves each hit by group: `brick`/`hard_clay` get `take_hit(3)` or are freed, `enemy`/`enemies` take 2 damage plus a 0.8 s stun, and `steel`/`border`/`buildings`/`base` block the move outright. Two consequences worth knowing: it is itself in `steel` + `buildings`, so roller walls cannot push each other or any other structure; and its terrain rules are a **seventh** hand-written copy of the group ladder — `tools/test_explosive_terrain_matrix.gd` does not cover it, `tools/test_roller_wall_and_stage2_destruction.gd` does.

**`buildings/wooden_wall.gd` (可移动木墙 / Movable Wooden Wall):** Joins `building` + `buildings` + `wooden_wall` + `wood` + `destructible`. Built with interlocking clay logs, iron straps, and sled skids. Can be moved/pushed both by tank physical contact (`take_push`) and kinetic projectile hits (`take_hit_direction`), sliding 48 px along the push axis with 4-frame dynamic motion and dust effects (`wooden_wall_f0..f3.png`). When sliding into obstacles, it crushes bricks and hard clay, deals 2 damage and a 0.6s stun to enemies, and takes 1 impact damage if blocked by solid walls. It features 3 visual damage stages (`wooden_wall_dmg0..2.png`), and upon destruction releases a 48px splinter blast dealing 1 AoE damage to adjacent enemies while spawning wood debris particles (`wood_debris_f0..f3.png` via `VFXAnimator.spawn_wood_debris`). Covered by `tools/test_wooden_wall.gd`.

**`buildings/pipe_conduit.gd` redirects bullets rather than destroying terrain, so it sits outside that ladder entirely.** It's a shop-bought (30 G) 90° elbow — hit it from its configured entry side and the bullet exits redirected instead of being destroyed; hit it from any other side and it takes damage like a normal structure (`handle_bullet_hit()`, wired from `bullet.gd`). It's also the one place in the project where a self-referencing enum on a `class_name` script tripped Godot 4.5's type checker: `@export var orientation: Orientation = Orientation.LEFT_TO_UP` fails because the enum-constant expression infers as `PipeConduit.Orientation` while the bare type annotation resolves to `Orientation`, and the checker treats those as different types. The fix is fully qualifying both sides (`PipeConduit.Orientation` throughout) — worth knowing before adding another `@export`ed enum to a `class_name` script.

### Audio

`SoundManager` (`scripts/sound_manager.gd`) synthesizes `AudioStreamWAV` buffers procedurally per call (square/sine/sawtooth/noise sweeps), attaches a throwaway `AudioStreamPlayer` to the scene root, and frees it on `finished`. There are no audio files in the repo.

### UI

`ui_theme_helper.gd` is a static-only style/widget factory: clay-styled buttons/panels/progress bars, the structure hotbar (`create_hotbar_ui` / `_rebuild_hotbar_slots` / `update_hotbar_stock` / `update_hotbar_selection`), the boss bar, and the victory/defeat modal. Dialogs (`shop_dialog`, `event_dialog`, `upgrade_selection_dialog`, `stage_preview_dialog`) build their controls in code and apply these. `vfx_animator.gd` is the counterpart for transient sprite-sequence effects (muzzle flash, clay debris, dust, shockwave, suicide blast, teleport burst, wormhole swirl) and also pokes `darkness_fog.gd` so flashes light up night-mode maps.

The SUICIDE truck's detonation is the one blast with its own dedicated sequence (`vfx_suicide_blast_f0..f5`, via `spawn_suicide_blast()`), drawn deliberately larger and slower than the generic `explosion.tscn` because its AoE is 84px — the visual has to match the kill radius or players cannot learn how far to run. Its read is a **green core that burns out**: the truck carries a green-emissive `mat_nuke`, so the explosion inheriting that green is what ties the blast to the thing that caused it. Green belongs to the core and inner ring only — two earlier attempts painted the whole mass green (a smooth green slime ball) or scattered green through the outer ring (orange/green patchwork reading as camouflage). `_suicide_detonate()` deliberately does **not** also spawn `explosion.tscn`: the small generic fireball muddied the green tell, and `explosion.gd::_ready()` plays its own `play_explosion()`, which double-triggered the sound.

### Progression numbers

Tuning constants are inlined at their use sites, not in a config: enemy stats and per-floor/lap scaling in `enemy.gd::_setup_tank_type()`, floor-gating in `main.gd::ENEMY_MIN_FLOOR`, level curve and stat multipliers in `rpg_manager.gd`, structure prices in `shop_dialog.gd::BUILDING_ITEMS`, encounter size / spawn rate / concurrent-enemy cap in `main.gd::{ENCOUNTER_BASE, SPAWN_INTERVAL_BASE, MAX_ALIVE_BASE}` (read through the static `encounter_size()` / `spawn_interval_for()` / `max_alive_for()` so tests can call them without booting `main.tscn`), `challenge_mode` specifics still inline in `start_game()`, and shop/rest/event outcomes in `event_dialog.gd::_on_choice()`.

**The gold economy has exactly one sink.** Kills do **not** award gold directly — `enemy.gd::_die()` drops a coin worth `gold_value` with 40% probability, and that coin has to be physically driven over (25 s lifetime, 120 px magnet). Events are net-neutral to net-positive (they charge 60–100 G but hand back 50–150 G). So the shop is the only place gold actually leaves the player. Income per regular-battle floor runs ~89 G on floor 0 to ~719 G on floor 14 (≈8× — enemy composition shifts to richer types *and* `floor_mult` applies), totalling **~5700 G** over an optimally-routed act.

The metric that matters is **surplus ratio = act income ÷ what the act's shops can absorb** (every shelf bought out, at that floor's prices). Above 1 means gold stops being a resource. Measured over 500 generated acts by `tools/probe_balance_report.gd`:

| | mean | median | p90 | max |
|---|---|---|---|---|
| before | 1.07 | 0.87 | 1.94 | 6.37 |
| now | **0.68** | 0.66 | 1.01 | 1.34 |

`tools/test_shop_pricing.gd` locks the structural half of this:

- **Prices scale with floor** (`ShopDialog.PRICE_FLOOR_SLOPE`, 0.12 — floor 14 costs 2.68×). The table's numbers are floor-0 prices. Deliberately steeper than the 0.08 the rewards use: at 0.08 the median act could buy nearly the whole shelf (0.87), i.e. the shop was just handing out everything you could reach. The slope only bites late — floor 0–2 prices are untouched, because the early floors are the tutorial band and being broke there reads as a broken system, not as difficulty.
- **Reroll escalates within a visit** (`REROLL_BASE` + `REROLL_STEP` × n, reset in `setup_shop()`). It used to be a flat 20 G with no limit, which made the "6 random of 11 upgrades" shelf purely decorative: one late floor's income buys thirty rerolls, so you just spin until the item you want appears.
- **Every floor guarantees `FloorMap.MIN_SHOPS_PER_FLOOR` (1, plus a second on floors of ≥13 rooms) reachable shop rooms.** `add_structure_stock()` is called **only** from `shop_dialog.gd`, so a shopless floor half-disables the builder while looking to the player like bad luck rather than a bug.

  The guarantee changed shape along with the map. On the spire DAG it had to be "3 shops *on a single route*", because the player climbed one path and shops on unreachable branches were worth nothing — `_ensure_shop_coverage()` DP'd the best route and converted nodes to hit the quota. A room graph is **undirected and fully connected**: the player can backtrack, so every shop on the floor is reachable and "which route" isn't a thing. `tools/test_shop_pricing.gd` accordingly asserts *count plus reachability* — reachability separately, because shops are assigned to dead ends and dead ends are derived from door adjacency, so a door-generation bug would produce a shop room that exists with no way in, which a count-only check passes happily.

  Historical measurement, kept because the mechanism still holds: on the old DAG, route shop count alone drove the surplus ratio (1 shop → 3.82, 3 → 1.12, 7 → 0.29), 17.5% of acts drew a 1–2-shop best route, and the guarantee *cost* income because a converted node is a battle you no longer fight (7555 G at 1 shop → 3929 at 7). Farm-or-shop is the intended trade.

⚠️ **The surplus-ratio baselines in the table above are stale and must be re-measured.** They were taken on the spire DAG. Both sides of the ratio moved: income went from "a dozen battles along one route" to "every combat room on the floor", and the spend cap went from "3 guaranteed shops per act" to 1–2. `tools/probe_balance_report.gd::_floor_econ()` has been rewritten to walk the room graph in BFS order (order matters, since prices and rewards both scale with `current_floor` = rooms cleared), but nobody has run the 400-act sampling to set a new baseline. Do that before tuning any price constant.

**Balance is not verifiable by reading these constants — measure it.** Because they're spread across five files and interact multiplicatively, several severe imbalances survived a long time while every constant looked individually reasonable. `tools/test_enemy_balance_curve.gd` drives the *real* `main.gd::_request_spawn_enemy()` path (never a replicated roll table — a copy drifts) and asserts four invariants that had each been violated:

- **Player damage must not outrun enemy HP.** `get_atk_damage()` is `1 + atk_bonus`, and `_auto_level_bonus()` used to grant `atk_bonus += 1` *every* level, i.e. damage == level, linear and unbounded. The measured result was a **100% one-shot rate from floor 4 to the end of the act** — including the 14 HP TRAIN_BOSS and the 10 HP BOSS. The whole HP-tier dimension (ARMOR 4 / BATTLESHIP 6 / TRAIN_BOSS 14) was dead: tanky units weren't tanky, only differently shaped. Damage now grows on `RPGManager.ATK_LEVELS_PER_POINT` (+1 per 4 levels, first point at level 3).

  Killing the 100% case wasn't enough: at +1 per 3 levels the floor 5–13 one-shot rate still averaged **68–71%**, so the HP tiers were still invisible most of the time. It's now 44%, gated by `LATE_ONE_SHOT_CEILING` (60%, sitting in the gap between those two clusters — see the in-file comment for why not 55%).

  Three dead ends worth not repeating:

  - **Don't fix this by scaling enemy HP with a floor multiplier.** Raising the HP-only floor slope (0.08 → 0.11) measured *worse* (STK 1.37 → 1.27): HP grows ~2.5× across an act while damage grows ~8×, so the slope has an order of magnitude too little authority. And it's the wrong axis entirely — see "Enemy toughness is integer and visible" below. The brake belongs on player damage growth, which isn't "secretly buffing enemies" — it's letting the roster's *existing* HP tiers stay legible.
  - **`ATK_FIRST_POINT_LEVEL = 3` is load-bearing, not an off-by-one.** Plain `level % 4` puts the first point at level 4, but a player finishes floor 0 at about level 3 — so floor 1 has damage 1 against a BASIC whose 1 HP had been `ceil()`ed to 2 by the old floor scaling, and the one-shot rate fell off a cliff from 100% to **0%**. "Trash dies in one shot" is the Battle City baseline; removing it on the second floor reads as a broken gun, not as difficulty. Starting at level 3 grants the identical 6 points per act (3/7/11/15/19/23), just one level earlier.
  - **Don't assert on shots-to-kill.** It looks like the right continuous metric and it isn't: integer damage means each +1 flips a large slice of the population between 1 and 2 shots, so per-floor STK sawtooths between 1.24 and 2.01 and which window looks higher depends purely on where sampling lands on the teeth. It's still logged; the assertion uses a multi-floor mean one-shot rate instead.
- **Difficulty must ramp inside an act.** Encounter HP used to sit flat at 58–69 from floor 5 to 14 — ten floors where only the rewards grew.
- **TRAIN_BOSS is encounter identity, not filler.** It sets `active_boss_instance` and lights the HUD boss bar. It was 17–21% of regular-battle spawns (the single most common type past floor 5) while being 0% of elite/boss *filler* — the boss unit was 3–4× more common outside boss fights than in them, and the boss bar was near-permanently on, retargeted by each new train.
- **The floor gate must not flatten the roster.** `_gate_enemy_type()` used to dump every not-yet-unlocked roll into `FAST`, so floor 3's eight-entry table measured **62% FAST** — more monotonous than floor 2, despite reading as the most varied tier. It now re-rolls among types actually unlocked at that floor (`GATE_FALLBACK_POOL`).

Two measurement gotchas, both learned the hard way:

- Count enemies at `child_entered_tree`, **not** by tallying survivors after a delay. 160 tanks share three spawn points, and SUICIDE's 84px blast kills its neighbours — a survivor tally reads TRAIN_BOSS at 26% against a true 15%, and SUICIDE at 0%, because the sample skews toward whatever has the most HP.
- **Wait for spawning to finish, never `await create_timer(N)`.** `_request_spawn_enemy()` doesn't create a tank; it drops a `spawn_star` and the tank only appears from that star's `finished` callback. A fixed sleep races the animation: under load the sampler captured **zero** tanks and reported "average HP 0.00", which reads as a balance collapse rather than a test that didn't wait. It hit ~17% of runs and *stopped reproducing the moment a `print` was added* — a textbook heisenbug that re-running will never diagnose. Both samplers now poll until the arrival count stops growing (`_await_spawns()`).

  **Polling wasn't enough, and the residue had a second cause worth knowing: a paused SceneTree.** `spawn_star` advances its timer in `_process(delta)`, so a paused tree means `finished` never fires and no tank ever appears — forever, not just slowly. The pause comes from gameplay: 140 sampled enemies fight each other, kills award XP, XP levels the player up, `main.gd::_on_rpg_level_up()` opens the upgrade dialog, and `upgrade_selection_dialog.gd` sets `get_tree().paused = true`. Headless nobody picks an option, so it stays paused — and `paused` lives on the **SceneTree**, so `_main.free()` doesn't clear it and *every subsequent sample* returns zero too. That's what made it look unrecoverable: retrying the measurement can't help. The tell is a diagnostic showing 140 stars created, 0 tanks arrived. `_await_spawns()` now force-clears `paused` each frame — the sampler doesn't care about level-ups. Measured 3/6 failing → 10/10 passing with zero retries.

  Corollary for any future headless test that boots `main.tscn` and lets it run: **the upgrade dialog can pause the tree out from under you**, and the pause outlives the scene.

#### The player side — measure the denominator too

Everything above measures enemies. Balance is a ratio, so an accurate enemy curve proves nothing on its own; `tools/probe_player_power.gd` measures the other half (DPS by branch, effective HP, where the fire-cooldown floor binds), and `tools/test_player_power.gd` gates it. The first run found four problems, all invisible from reading the constants:

- **Regen was a hidden second health bar.** `get_regen_rate()` ticked unconditionally at 1.5 HP/s by level 24, so a 45 s battle healed 67.5 HP against a 9 HP maximum — effective HP 76, and **enemies needed an 83% hit rate to out-damage it**. In a game where you're always moving and terrain eats bullets, that meant ordinary bullets could not kill a late-act player at all; only burst damage (SUICIDE 3, BOMBER 3) mattered. `player.gd::REGEN_COMBAT_LOCKOUT` (3 s, cleared accumulator) turns it into a reward for disengaging: the required hit rate is now 23%.

  Computing that threshold needs a **fixed point, not a division** — hit rate and regen uptime depend on each other (hitting more often keeps the lockout up, which cuts regen). Both the probe and the gate bisect for it. Uptime itself is `e^(-λL)`: the chance of no hit within the last `L` seconds, treating incoming fire as Poisson.

- **The `train` branch was being diluted by its own growth curve.** Carriage bullets were hardcoded to damage 1 and 2 and never read `atk_bonus`, so as the main gun climbed to 7 the two carriages fell to **14%** of total output, leaving train at ~25 DPS against heavy 37 / speed 39 with only +3 HP to show for it. Carriage damage is now `base + atk_bonus / 2` (half, not full — at full damage two carriages would triple train's output and flip the imbalance the other way). Share is back to 33%, train totals ~32.
- **The shop sold an item that does nothing.** `player.gd::_fire()` clamps cooldown to 0.18 s (speed) / 0.32 s (others). Past that, every further fire-rate source is worth exactly zero — and with `rapid_loader` stacked to 3, the clamp binds at **level 10** of a ~24-level act. The 90 G `autoloader` card kept selling and the level-up screen kept offering `rapid_loader`, both still advertising "+10% reload". Fixed the same way the perk-cap bug was: the check lives in the buy/offer path (`RPGManager.is_fire_rate_capped()`), not in a post-hoc refund.
- **`heavy` won the branch choice before it started.** `+2` damage and `+2` HP at tier 0, against a tier-0 baseline of 1 damage and 1 HP — 1st-level DPS was **2.55×** default where speed was 1.70×. Since the branch screen appears at the first level-up with no skip option, that's just telling the player what to pick. `HEAVY_BONUS_BASE` is 1 now, so the opening spread is 1.70× and the branches separate on tier instead.

Two testing notes from writing that gate, both of which produced a wrong result first:

- **Assert on behaviour, not on the constant.** The first regen check only read `REGEN_COMBAT_LOCKOUT`, which passes fine if someone keeps the constant and deletes the assignment. The behavioural version (damage the player, check the lockout armed and the accumulator cleared) immediately failed for a reason worth knowing: `player.gd::_ready()` calls `set_invulnerable(3.5)`, so a freshly spawned player ignores `take_damage()` entirely.
- **Instantiate scenes, not scripts.** `TrainCarriage.new()` leaves `@onready var sprite = $Sprite2D` unresolved and prints a screenful of "Node not found". Load the `.tscn`.

#### The balance log

The gates above answer "did it pass". They can't answer "is this better than last week", which is the question you actually have while tuning — so measurements get written to `logs/balance/*.jsonl` (gitignored) and read back by a statistics script.

```powershell
& $godot --headless --path . --script tools/probe_balance_report.gd      # enemies: ~4 min
& $godot --headless --path . --script tools/probe_balance_report.gd -- --samples 120 --acts 800
& $godot --headless --path . --script tools/probe_player_power.gd        # players: instant
python tools/analyze_balance_log.py                    # default report
python tools/analyze_balance_log.py --cat enemy_roll --field hp --by floor
python tools/analyze_balance_log.py --vs <commit>      # before/after, with Welch t
python tools/analyze_balance_log.py --list --sessions --tests
```

Three producers write to it, all via `scripts/balance_log.gd` (`emit` / `emit_batch`, one JSONL file per category, always appending, tagged with `_session` + `_commit` + `_ts`):

- **`tools/probe_balance_report.gd`** — the sampler. It's a *ruler*, not a gate: no assertions, it just drives the real spawn/economy paths and dumps `enemy_roll` (one row per spawned tank), `floor_econ` (per floor × battle type), and `act_econ` (per generated act). It instantiates `main.tscn` once per (floor × battle_type) — 46 times — rather than per act, because the roll table depends only on that pair; the 400–500 act-economy runs then reuse those aggregates and are pure computation. Doing it the naive way is ~70× slower for zero extra information.
- **`tools/test_enemy_balance_curve.gd`** and **`tools/test_shop_pricing.gd`** — the gates also log what they measured (`curve_gate`, `route_shops`), so every test run contributes a data point for free.
- **`main.gd::_game_over()`** — a `battle_result` row per real battle played. This is the only source that captures what the probe structurally cannot: the probe assumes every coin is collected, but coins are physical pickups with a 25 s lifetime, so **expected income ≠ banked income** and only actual play measures the collection rate.

Notes for anyone extending it:

- `BalanceLog.session_id()` uses `Time.get_ticks_usec()`, **never `randi()`**. The Daily Challenge seeds the global RNG in `start_game()` and then depends on that stream being deterministic; drawing one number from it at an arbitrary moment desyncs everyone's run for that day.
- Logging is off outside debug builds and can be forced off with `TANK_BALANCE_LOG=0`.
- `analyze_balance_log.py` needs only numpy. Normality is Jarque–Bera (skew + kurtosis only, no scipy), and the report says so, along with the two ways to misread it: *most of these metrics shouldn't be normal* — enemy HP is a handful of discrete tiers, and the check's real use is telling "continuous, as I assumed" apart from "actually three spikes". Act income, being a sum over ~10 floors, *should* approach normal by CLT; if it doesn't, one floor is dominating, and that's the finding.

## Conventions

- `class_name` on nearly every script; siblings are still pulled in with `const X = preload(...)` at the top (both idioms coexist — follow the file you're in).
- Comments in the GDScript are mixed English/Chinese; keep whatever a file already uses. Long block comments explaining *why* a design was chosen (and what the previous broken version did) are the house style — preserve them when editing nearby code.
- Player input is per-player action sets (`p1_*` / `p2_*`); the legacy `move_*`/`fire` actions remain in `project.godot` but are unused by `player.gd`. Gamepad device 0 → P1, device 1 → P2.
- **Everything playable must be an input action, not a raw keycode.** Movement and firing always had gamepad bindings, but building was an `event.keycode == KEY_Q` chain in `builder_controller.gd::_unhandled_input`, which locked the entire structure system to the keyboard. It now goes through `p{1,2}_build_{prev,next,place,cancel}`; the keyboard keys are unchanged (Q/Z, E/C, F, R for P1; U/J, O/L, K/Enter, Backspace for P2) and simply live inside those actions. Numeric 1–6 quick-select stays a raw keycode — it's a keyboard-only convenience with no gamepad analogue.
- **Gamepad button budget.** Godot 4 `JoyButton`: 0=A 1=B 2=X 3=Y 4=BACK 6=START 9=LB 10=RB 11–14=D-pad. Taken: D-pad + left stick = move, A and RB = fire, LB/X/Y/BACK = build prev/next/place/cancel, START = pause (and restart, see below). **Do not bind gameplay to B** — it is Godot's built-in `ui_cancel`, i.e. "back" in menus, so anything else on B fires twice at once. `builder_controller.gd` carries the same warning about ESC for the same reason.
- `pause` (ESC / P / START) is a real action rather than a reuse of `ui_cancel`, so that B is free for menu navigation. `restart` also sits on START, which is safe only because `main.gd` reads it exclusively while `is_game_over or is_victory`, and the pause handler excludes exactly those two states.
- **Menus need `UIThemeHelper.focus_first()`.** Godot gives no Control initial focus, and without focus there is nothing for `ui_up`/`ui_accept` to act on — before this the whole game was mouse-only from the title screen onward. Call it at the end of whatever method makes a screen visible (`_ready()` for title/map, `setup_*()` / `show_upgrade_options()` for the dialogs, since those are hidden at `_ready()` time). It defers the `grab_focus()` because code-built controls are not laid out on the frame they are created, and it skips hidden and disabled buttons — the title screen's "continue" button is hidden when there is no save.
